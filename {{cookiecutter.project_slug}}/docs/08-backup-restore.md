# 8. Backup and restore

Two procedures. The backup half is easy and everybody writes it. The restore half is the one that
matters, and it must be written by somebody who has actually performed it.

**A backup that has never been restored is not a backup.**

## What is backed up

| Item | Backed up | Why |
|---|---|---|
| PostgreSQL database | Yes | All content, users, submissions, e-mail log, audit log |
{%- if cookiecutter.media_storage == "filesystem" %}
| `MEDIA_ROOT` | Yes | Uploaded images and documents; not in git |
| `PRIVATE_MEDIA_ROOT` | Yes | Uploads containing personal data; not in git, and not web-reachable |
{%- else %}
| Object store, `media/` prefix | Yes — **by versioning, not by copying** | Uploaded images and documents; not in git. See "Media is versioned, not rsynced" below |
| Object store, `private/` prefix | Yes — same mechanism | Uploads containing personal data; not in git, and not web-reachable |
{%- endif %}
| `.env` and other secrets | Yes, separately and encrypted | Without them the restored code will not start |
| Web server, TLS and cron configuration | Yes | Rebuilding these from memory is where a restore overruns |
{%- if cookiecutter.media_storage != "filesystem" %}
| Bucket policy, lifecycle rules and IAM bindings | Yes, as code or as a written record | A restored bucket with a permissive policy is worse than no bucket. Rebuilding it from memory during an incident is how private files become public |
{%- endif %}
| Application source code | No | It lives in git, tagged per release |
| `staticfiles/`, `.mo` files, image renditions, `.venv` | No | Derived; regenerated by the deploy |

rsync -a --delete \
      --backup --backup-dir="/var/backups/{{ cookiecutter.project_slug }}/media-deleted/$(date +%F)" \
      /srv/{{ cookiecutter.project_slug }}/media/ /var/backups/{{ cookiecutter.project_slug }}/media/

rsync -a --delete \
      --backup --backup-dir="/var/backups/{{ cookiecutter.project_slug }}/private-media-deleted/$(date +%F)" \
      /srv/{{ cookiecutter.project_slug }}/private-media/ /var/backups/{{ cookiecutter.project_slug }}/private-media/
{%- else %}

# Media is NOT copied here. See the next section.
{%- endif %}

# Push off-server, encrypted and deduplicated, to the agreed remote
restic -r "$RESTIC_REPOSITORY" backup /var/backups/{{ cookiecutter.project_slug }}
restic -r "$RESTIC_REPOSITORY" forget --keep-daily 30 --keep-weekly 8 --keep-monthly 12 --prune
```

The job **must exit non-zero on failure and that failure must raise an alert**. A backup job that
fails silently for three weeks is discovered on the day it is needed.

## Media is versioned, not rsynced

This is the part of the backup story that changes when media moves into an object store, and it is
the part that gets missed, because "we back up nightly" keeps being true of the database and quietly
stops being true of the files.

There is no media directory on the server to copy. The nightly `rsync` is replaced by settings **on
the bucket** — configuration that is applied once and then has to be verified, not a cron job that
either ran or did not:

{% if cookiecutter.media_storage == "s3" -%}
1. **Versioning on.** Every overwrite and every delete keeps the previous object as a noncurrent
   version, and a delete leaves a delete marker rather than removing anything. This is what makes an
   accidental deletion recoverable — and it only protects objects written *after* it was enabled, so
   it must be on before the first upload.
2. **A lifecycle rule** that expires noncurrent versions after the agreed retention (90 days by
   default) and aborts incomplete multipart uploads after 7 days. Without it, versioning is a bill
   that grows forever and nobody ever measures.
3. **MFA delete, or a separate replication target.** Versioning protects against a mistake; it does
   not protect against an attacker who holds credentials that can permanently delete versions. See
   the IAM boundary in [03-infrastructure.md](03-infrastructure.md).
4. Optionally, **cross-region replication** to a bucket in a different account. That, not versioning,
   is what survives the account itself being lost.

1. **Blob versioning on**, plus **soft delete for blobs and for containers**. Versioning keeps the

   container — recoverable for the configured window. Versioning only protects blobs written *after*

2. **A lifecycle management rule** that deletes previous versions after the agreed retention (90 days

   deleting versions. Versioning protects against a mistake; it does not protect against an attacker

   versioning, is what survives the subscription itself being lost.

Two consequences to be clear about with the client, in writing, before go-live:

- **Versioning lives in the same account as the data it protects.** An account compromise, a billing
  suspension or a mistaken account deletion takes the versions with it. If the agreement requires
  survival of that, an off-provider copy is required and it is a separate, funded piece of work.
- **The database and the media are no longer captured at the same instant.** A database restored to
  last night points at objects whose current version may be newer. Object versioning is what lets you
  roll the affected objects back to the same point; nothing does it automatically.
{%- endif %}

## Where backups are stored

- **A backup on the same server is not a backup.** Every backup is copied off the application
  server, out of its failure domain. A local copy is acceptable only as an additional fast-restore
  tier.
- Three copies (production plus two backups), on two distinct storage systems, at least one
  off-site.
- Encrypted at rest, client-side, before upload. Vendor server-side encryption is accepted only in
  addition, never instead.
- Encrypted in transit over SSH or TLS. No plain FTP, ever.
- The encryption passphrase is **not stored on the application server** and not in the same store as
  the backup credentials.
- Write credentials are append-only where the storage supports it, so a compromised application
  account cannot delete the history.
{%- if cookiecutter.media_storage != "filesystem" %}
- **Bucket versioning satisfies none of the rules above**, because the versions sit in the
  same account, on the same storage system, in the same failure domain as the live data. It is
  excellent protection against a mistake and no protection against losing the account. Treat it as
  the fast-restore tier and be explicit with the client about what it does not cover.
{%- endif %}

### Step 0 — Stop

A restore is never started by one person alone.

1. Tell the project lead and the client contact. Write down the authorisation, the chosen restore
   point and the expected data loss **before** step 1.
2. Stop the application so nothing writes during the restore:

```bash
{% if cookiecutter.deploy_target == "gunicorn_nginx" %}sudo systemctl stop {{ cookiecutter.project_slug }}-gunicorn{% else %}docker compose stop web{% endif %}
```

3. **Back up the broken state first.** You may need it, and you cannot get it back afterwards.

```bash
pg_dump --format=custom --no-owner --no-privileges \
        --file="/var/backups/{{ cookiecutter.project_slug }}/pre-restore-$(date +%F-%H%M).dump" "$DATABASE_URL"
{%- if cookiecutter.media_storage == "filesystem" %}
tar -czf "/var/backups/{{ cookiecutter.project_slug }}/pre-restore-media-$(date +%F-%H%M).tar.gz" \
        /srv/{{ cookiecutter.project_slug }}/media /srv/{{ cookiecutter.project_slug }}/private-media
{%- elif cookiecutter.media_storage == "s3" %}
# Media: versioning already preserves the current state, so there is nothing to
# copy - as long as you write down the timestamp you are working from. Do that.
date -u +%FT%TZ | tee /var/backups/{{ cookiecutter.project_slug }}/restore-started-at
{%- elif cookiecutter.media_storage == "gcs" %}
# Media: object versioning already preserves the current state, so there is
# nothing to copy - as long as you write down the timestamp you are working
# from. Do that.
date -u +%FT%TZ | tee /var/backups/{{ cookiecutter.project_slug }}/restore-started-at
{%- else %}
# Media: blob versioning already preserves the current state, so there is
# nothing to copy - as long as you write down the timestamp you are working
# from. Do that.
date -u +%FT%TZ | tee /var/backups/{{ cookiecutter.project_slug }}/restore-started-at
{%- endif %}
```

### Step 1 — Choose the restore point

```bash
restic -r "$RESTIC_REPOSITORY" snapshots
```

Choose the newest snapshot **before** the problem started. For corruption discovered late, that is
not the newest snapshot.

### Step 2 — Retrieve it

```bash
restic -r "$RESTIC_REPOSITORY" restore <snapshot-id> --target /var/restore
```

### Step 3 — Restore the database

```bash
pg_restore --clean --if-exists --no-owner --no-privileges \
           --dbname="$DATABASE_URL" \
           /var/restore/var/backups/{{ cookiecutter.project_slug }}/db-<timestamp>.dump
```

### Step 4 — Restore media

{% if cookiecutter.media_storage == "filesystem" -%}
```bash
rsync -a --delete /var/restore/var/backups/{{ cookiecutter.project_slug }}/media/ \
                  /srv/{{ cookiecutter.project_slug }}/media/
rsync -a --delete /var/restore/var/backups/{{ cookiecutter.project_slug }}/private-media/ \
                  /srv/{{ cookiecutter.project_slug }}/private-media/
sudo chown -R {{ cookiecutter.project_slug }}:{{ cookiecutter.project_slug }} \
     /srv/{{ cookiecutter.project_slug }}/media /srv/{{ cookiecutter.project_slug }}/private-media
```

Ownership matters. A restore that leaves media owned by root produces a site where every image
returns a permission error, which looks like a different fault entirely.
{%- else -%}
**There is no bulk media restore, and in most incidents there must not be one.** Objects are keyed by
generated UUID and are never overwritten in normal operation, so a database restored to an earlier
point still finds every object it references. Rolling the whole bucket back would instead *delete*
files uploaded since the restore point that the restored database has no rows for — losing data to
fix a data loss.

So decide which case this is first:

**Case A — the database was restored, the bucket is intact.** Do nothing here. Go to step 5. Objects
belonging to rows that no longer exist are orphans: leave them, and sweep them in a separate,
reviewed job once the incident is closed.

**Case B — specific objects were deleted or overwritten.** Restore only those, from their versions.

{% if cookiecutter.media_storage == "s3" -%}
```bash
# What versions exist for one key
aws s3api list-object-versions --bucket "$AWS_STORAGE_BUCKET_NAME" --prefix "private/<key>"

# Undo a delete: remove the delete marker
aws s3api delete-object --bucket "$AWS_STORAGE_BUCKET_NAME" \
    --key "private/<key>" --version-id "<delete-marker-version-id>"

# Undo an overwrite: copy the wanted version back over the current one
aws s3api copy-object --bucket "$AWS_STORAGE_BUCKET_NAME" \
    --copy-source "$AWS_STORAGE_BUCKET_NAME/private/<key>?versionId=<version-id>" \
    --key "private/<key>"
```
{%- elif cookiecutter.media_storage == "gcs" -%}
```bash
# What generations exist for one object
gcloud storage ls --all-versions "gs://$GS_BUCKET_NAME/private/<key>"

# Restore one generation over the current object
gcloud storage cp "gs://$GS_BUCKET_NAME/private/<key>#<generation>" \
                  "gs://$GS_BUCKET_NAME/private/<key>"
```
{%- else -%}
```bash
# What versions exist for one blob
az storage blob list --container-name "$AZURE_PRIVATE_CONTAINER" \
   --prefix "private/<key>" --include v --account-name "$AZURE_ACCOUNT_NAME"

# Restore one version over the current blob
az storage blob copy start --account-name "$AZURE_ACCOUNT_NAME" \
   --destination-container "$AZURE_PRIVATE_CONTAINER" --destination-blob "private/<key>" \
   --source-uri "https://$AZURE_ACCOUNT_NAME.blob.core.windows.net/$AZURE_PRIVATE_CONTAINER/private/<key>?versionid=<version-id>"
```
{%- endif %}

**Case C — the bucket itself is gone.** Recreate it, **apply the policy from
[03-infrastructure.md](03-infrastructure.md) before writing a single object**, then restore from the
off-provider copy if one exists. If none exists, the media is lost, and that was a decision recorded
before go-live rather than a surprise now.

A recreated bucket with a default policy is the worst possible outcome of a restore: it publishes
every CV in it. Applying the policy is step one, not a cleanup task.
{%- endif %}

### Step 5 — Configuration and matching code

Restore `.env` from the secrets backup, then bring the code to the release that matches the data.
Restoring last night's database under this morning's code runs migrations that were never tested
against that data.

```bash
cd /srv/{{ cookiecutter.project_slug }}
git fetch --all --tags
git checkout <tag-that-was-live-at-the-restore-point>
```

```

### Step 7 — Verify before declaring success

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://{{ cookiecutter.domain_name }}/healthz
{% if cookiecutter.frontend != "api_only" %}curl -sS -o /dev/null -w '%{http_code}\n' https://{{ cookiecutter.domain_name }}/{% if cookiecutter.languages == "en_ar" %}en/
curl -sS -o /dev/null -w '%{http_code}\n' https://{{ cookiecutter.domain_name }}/ar/{% endif %}
{% endif %}```

Then, by hand:

- [ ] Sign in to the administration interface{% if cookiecutter.use_2fa == "yes" %} and confirm the second factor is still enforced{% endif %}.
- [ ] Open the most recently edited content and confirm it is there.
- [ ] Open a media file — an image and a PDF — and confirm both load.
- [ ] Open a private-media file through the application and confirm it still requires permission.
{%- if cookiecutter.media_storage != "filesystem" %}
- [ ] Request a private object's URL directly, without a signature, and confirm it returns 403. On a
      recreated bucket this is the check that catches a policy that was never reapplied, and it is
      the difference between a restore and a data breach.
- [ ] Confirm versioning is still enabled on the bucket. A recreated bucket does not inherit it, and
      a restore that leaves versioning off leaves the site with no media backup at all.
{%- endif %}
- [ ] Count the newest rows in the main data table and note the newest timestamp. This is the number
      you will report as the data loss.
{%- if cookiecutter.forms_suite == "yes" or cookiecutter.newsletter == "yes" %}
- [ ] Submit a test form and confirm the notification e-mail arrives.
{%- endif %}
- [ ] Confirm the admin action log is present.

### After any restore

- Tell the client **exactly what was lost**: the restore-point timestamp and the newest surviving
  record.
- Write a post-incident note within two working days.
- If the cause was a compromise, rotate `SECRET_KEY`, the database password{% if cookiecutter.media_storage != "filesystem" %}, the object-store
  credentials{% endif %}, every third-party key, and force a staff password reset{% if cookiecutter.use_2fa == "yes" %}, and re-enrol second factors{% endif %} before the site
  is exposed again.{% if cookiecutter.media_storage != "filesystem" %} Then re-read the bucket policy: an attacker who held write credentials may
  have changed it, and a public-read bucket is a quiet, permanent version of the incident.{% endif %}

## Restore testing

- The first full test is completed **within two weeks of go-live**. Until it has been done, the
  project is not delivered.
- **Quarterly** thereafter, for the life of the hosting arrangement.
- After any change to backup configuration, schedule, storage target or encryption key.
- After any major PostgreSQL version upgrade.

A test is a full restore into a clean, isolated environment, following the runbook above end to end
from a stored backup. It is not `pg_restore --list` and it is not a checksum. **It is timed, and
that time is the evidence for the stated RTO.**

A test that reveals an error in the runbook is a successful test. Correct the runbook in the same
working session.

## Disaster scenarios

- **Total server loss.** Build a clean server ([03-infrastructure.md](03-infrastructure.md)), then
  follow the restore runbook. DNS propagation adds to the RTO, so production DNS records are kept at
  a 300-second TTL.{% if cookiecutter.media_storage != "filesystem" %} Media is unaffected: it was never on that server. This is the one scenario
  an object store makes materially better.{% endif %}
{%- if cookiecutter.media_storage != "filesystem" %}
- **Cloud account or subscription loss** — a billing failure, a mistaken deletion, a suspended
  account. Versioning does not help: the versions were in the account too. Only an off-provider copy
  survives this, and whether one exists is a decision recorded before go-live, not discovered now.
{%- endif %}
- **Corruption discovered late.** Do not restore the newest backup. Restore a pre-corruption
  snapshot into an isolated environment first, and prefer a targeted repair written as a reviewed
  management command run inside a transaction.
- **Ransomware or compromise.** Isolate the machine; do not reboot it, because memory is evidence.
  Assume every credential is compromised. Build a clean server, restore from before the earliest
  evidence, rotate every secret and re-enrol second factors before exposing the site, and fix the
  entry route. Tell the client immediately.
- **An editor deleted or overwrote something.**
{%- if cookiecutter.stack == "wagtail" %}
  Use the page's revision history. This is not a restore event, and it is the reason editors should
  unpublish rather than delete.
